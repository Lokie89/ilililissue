# 프로젝트 규칙

이 문서는 Codex가 새 프로젝트를 만들거나 기존 프로젝트에 처음 들어갈 때 적용하는 글로벌 기준이다.

로컬 프로젝트 정책은 실제 프로젝트 안에서 `local/<project-name>/` 문서로 만든다. 이 문서는 로컬 문서를 지금 채우기 위한 것이 아니라, 로컬 규칙이 없거나 부족할 때 어떤 대화와 하네스를 생성해야 하는지 정의한다. `local/`은 [Claude](../claude/project-rules.md) 등 다른 모델과 공유될 수 있으므로 산출물은 모델이 아니라 프로젝트 기준으로 둔다.

## 프로젝트 진입 기준

- 먼저 사용자 요청이 새 프로젝트 생성인지, 기존 프로젝트 수정인지, 단순 분석인지 분류한다.
- 이 문서 세트를 다른 프로젝트 루트로 복사했는데 루트 `AGENTS.md`, `CLAUDE.md`, 기본 `.codex/agents/`/`.claude/agents/` 에이전트가 없으면 `node scripts/bootstrap-project-root.mjs`로 생성한다. 기존 파일은 덮어쓰지 않는다.
- `ai-agents/` 디렉터리 자체를 다른 프로젝트 루트 안에 넣어 쓰는 nested 구성이라면, Codex가 이 문서 세트를 한 번이라도 읽었을 때 부모 루트에 얇은 `AGENTS.md`/`CLAUDE.md` 진입점이 있는지 확인하고 없으면 `node scripts/install-parent-entrypoints.mjs`로 생성한다. 기존 파일은 덮어쓰지 않는다.
- 루트 진입 문서만 보강하면 충분한 경우에는 `node scripts/ensure-entrypoints.mjs`를 사용할 수 있다.
- 새 프로젝트 생성이나 프로젝트 초기 세팅으로 분류되면 기본 동작은 청사진 먼저 제시이며, 사용자가 청사진 승인 또는 즉시 파일 생성을 명시하기 전까지 구현을 시작하지 않는다.
- 저장소 구조, 실행 파일, 설정 파일, lockfile, 테스트 파일, README를 확인한다.
- 해당 프로젝트의 로컬 문서가 있는지 확인한다.
- 로컬 문서가 있으면 글로벌 규칙보다 로컬 정책을 우선한다.
- 로컬 문서가 없거나 비어 있으면 구현 전에 필요한 범위의 로컬 하네스 대화를 생성한다.
- 단순 분석이나 코드 변경이 없는 질의는 로컬 하네스 생성을 강제하지 않는다. 단, 분석 결과 문서화 여부는 아래 `코드 분석 산출물` 기준을 따른다.

## 코드 분석 산출물

코드베이스나 아키텍처를 설명·요약·평가하는 분석 작업(짧은 단일 질의나 자명한 파일 확인은 제외)은 대화 안에만 남기지 않고 `local/<project-name>/analysis/`에 문서로 남긴다. 대화 컨텍스트에만 남으면 다음 세션이나 다음 질문에서 같은 분석을 토큰을 들여 반복하게 되므로, 결과를 재사용 가능한 문서로 고정한다.

- 로컬 하네스 전체(`goal.md` 등)가 없는 프로젝트에서도 분석 문서만 단독으로 만들 수 있다. 분석 문서 작성이 로컬 하네스 전체 생성을 강제하지는 않는다.
- 파일명은 `YYYY-MM-DD-<주제-슬러그>.md` 형식을 쓴다.
- 문서에는 분석 범위, 확인한 파일/경로, 핵심 결론, 후속 조치 또는 미정 항목을 포함한다.
- 같은 주제를 다시 분석해야 하면 새 문서를 쓰기 전에 `local/<project-name>/analysis/`에 기존 문서가 있는지 먼저 확인해 재분석을 줄인다.
- 분석 문서는 `handoff-log.md` 인계 기준과 별개다. 장기 작업 인계가 필요하면 `handoff-log.md`에서 해당 분석 문서를 링크로 참조한다.

## 로컬 하네스가 필요한 경우

아래 중 하나라도 해당하면 `local/<project-name>/` 하네스가 필요하다.

- 새 프로젝트를 생성한다.
- 도메인 개념, 엔티티, 상태, 권한, 생명주기, 불변 조건을 추가한다.
- 프로젝트 아키텍처, 기술 스택, 배포 구조, 서버 구성, 통신 방식, 데이터 저장소를 정해야 한다.
- 실행, 테스트, 빌드, 배포 방식이 프로젝트마다 달라진다.
- 환경변수, 비밀값, 외부 서비스, 데이터 저장소를 사용한다.
- 장기 작업이거나 다음 세션 인계가 필요하다.
- 글로벌 규칙과 다른 예외가 필요하다.

## 외부 연동 인터페이스 문서화

외부 시스템과 연결되는 어댑터, SDK 래퍼, API 클라이언트, Webhook, 메시지 큐, 이벤트 브로커, 파일 교환, 배치 연동을 추가하거나 변경하면 항상 인터페이스 문서를 남긴다. 코드 구현만으로 완료 처리하지 않는다.

- 문서 위치는 프로젝트의 `local/<project-name>/architecture.md`, `README.md`, `docs/` 중 기존 구조와 가장 가까운 곳으로 정하고, 로컬 하네스가 있으면 `architecture.md`에서 위치를 참조한다.
- 문서에는 연동 대상, 책임 경계, 호출 방향, 인증 방식, 요청·응답 또는 메시지 스키마, 오류·재시도·타임아웃 기준, rate limit, 멱등성, 비밀값 이름, 테스트 또는 대체 검증 방법을 포함한다.
- 외부 제공자의 최신 API 동작이나 제한은 기억으로 단정하지 않고 공식 문서나 1차 출처를 확인한다.
- 비밀값의 실제 값은 기록하지 않고 이름, 목적, 필요 여부만 기록한다.
- 아직 확정되지 않은 항목은 비워두지 않고 `미정` 또는 `해당 없음`으로 남긴다.

## 로컬 하네스 대화

로컬 규칙이 없거나 부족하면 한 번에 모든 것을 묻지 않고, 구현에 필요한 최소 질문부터 제시한다.

### 필수 질문

- 프로젝트 이름과 목적은 무엇인가?
- 새 프로젝트인가, 기존 프로젝트인가?
- 주요 사용자와 핵심 사용 흐름은 무엇인가?
- 사용할 기술 스택, 런타임, 패키지 관리자는 무엇인가?
- 기본 아키텍처 구성은 무엇인가? 단일 서버, 프론트/백 분리, 모듈러 모놀리스, MSA, BFF, API Gateway, 클러스터, 서버리스 중 어느 쪽인가?
- 예상 실행 환경과 PC 또는 서버 스펙은 무엇인가?
- 실행, 테스트, 빌드 명령은 무엇인가?
- 도메인 개념 중 아직 확정되지 않은 용어가 있는가?
- 환경변수, 비밀값, 외부 서비스, 데이터 저장소가 필요한가?
- 배포 또는 운영 영향이 있는가?

### 조건부 질문

- 인증, 권한, 개인정보, 결제, 데이터 삭제가 관련되는가?
- 마이그레이션이나 되돌리기 어려운 변경이 있는가?
- 실패해야 하는 입력, 금지 상태, 허용되면 안 되는 상태 전이는 무엇인가?
- UI가 있다면 주요 화면, 반응형 기준, 접근성 요구가 있는가?
- API가 있다면 소비자, 인증 방식, 오류 응답 기준은 무엇인가?
- 데이터 저장소, 캐시, 검색엔진, 오브젝트 스토리지, 메시지 큐, 이벤트 브로커, 스케줄러가 필요한가?
- REST, GraphQL, gRPC, WebSocket, 이벤트 기반 통신 중 필요한 방식이 있는가?
- 단일 서버에서 시작하더라도 나중에 분리하거나 확장해야 하는 경계가 있는가?

## 로컬 하네스 산출물

필요한 답을 얻으면 아래 파일을 생성하거나 갱신한다.

```text
local/<project-name>/
  goal.md
  context-map.md
  domain-policy.md
  architecture.md
  tools.md
  validation.md
  handoff-log.md
```

새 로컬 문서는 `local/_template/`의 템플릿을 우선 사용한다. 템플릿이 없는 경우 아래 역할 표를 기준으로 최소 구조를 만든다.

각 파일의 역할은 아래와 같다.

| 파일 | 역할 |
| --- | --- |
| `goal.md` | 프로젝트 목표, 제외 범위, 완료 기준 |
| `context-map.md` | 코드, 문서, 데이터, 설정 위치 |
| `domain-policy.md` | 도메인 용어, 상태, 권한, 생명주기, 미결 질문 |
| `architecture.md` | 기술 스택, 실행 환경, 배포 구조, 통신 방식, 데이터 저장소, 운영 전제 |
| `tools.md` | 프로젝트별 허용 도구, 금지 도구, 승인 필요한 명령 |
| `validation.md` | 실행, 테스트, 빌드, 린트, 배포 전 검증 |
| `handoff-log.md` | 변경, 검증, 남은 작업, 주의 사항 |

## 새 프로젝트 생성 기준

새 프로젝트를 만들 때는 최소한 아래 산출물을 남긴다.

- 구현 전에 프로젝트 목적, 아키텍처, 기술 스택, 로컬 하네스, 검증 방법, 미정 항목이 포함된 청사진
- 실행 가능한 기본 애플리케이션 또는 라이브러리 구조
- README의 설치, 실행, 테스트 명령
- 현재 기준의 아키텍처 청사진
- 필요한 경우 `.env.example` 또는 환경변수 문서
- 외부 연동 어댑터, API, 메시지, 파일 교환이 있으면 인터페이스 문서
- 기본 테스트 또는 가장 가까운 검증 명령
- 로컬 하네스 문서
- 실패한 검증과 미실행 검증의 이유

## 새 프로젝트 기본 완료 체크리스트

- 첫 화면, CLI 도움말, API health check 중 프로젝트 유형에 맞는 진입점이 동작한다.
- 사용자가 요청한 핵심 흐름이 최소 1개 이상 동작한다.
- 오류 상태 또는 빈 상태가 하나 이상 정의되어 있다.
- README만 보고 설치, 실행, 검증을 재현할 수 있다.
- 외부 서비스가 필요한 경우 실제 비밀값 없이 `.env.example` 또는 환경변수 표가 있다.
- 외부 연동 어댑터, API, 메시지, 파일 교환이 있으면 인터페이스 문서가 있다.
- 아키텍처 청사진에 배포 단위, 기술 스택, 데이터 저장소, 운영상 미정 항목이 기록되어 있다.
- 테스트가 없으면 테스트를 만들지 못한 이유와 대체 검증 방법이 `validation.md`에 남아 있다.
- 생성된 파일과 실행하지 못한 검증이 최종 보고에 포함된다.

## 프로젝트 유형별 최소 기준

| 유형 | 최소 동작 | 최소 검증 |
| --- | --- | --- |
| 웹앱 | 첫 화면과 핵심 사용자 흐름 1개 | 빌드 또는 실행 확인, 가능하면 UI/단위 테스트 |
| API 서버 | health check와 핵심 엔드포인트 1개 | 서버 시작 확인, 엔드포인트 호출, 가능하면 API 테스트 |
| CLI | help 출력과 핵심 명령 1개 | 명령 실행 확인, 가능하면 단위 테스트 |
| 라이브러리 | 공개 API 예시 1개 | 단위 테스트 또는 샘플 실행 |
| 문서/하네스 | 링크와 필수 섹션 | 문서 검증 스크립트 또는 대체 검증 |

## 기존 프로젝트 수정 기준

기존 프로젝트에서는 새 구조보다 기존 패턴을 우선한다.

- 관련 파일과 테스트를 먼저 확인한다.
- lockfile과 패키지 관리자 기준을 따른다.
- 로컬 하네스가 없더라도 작은 단일 수정은 바로 진행할 수 있다.
- 도메인, 아키텍처, 실행, 검증, 배포 방식이 불명확하면 로컬 하네스 대화를 먼저 생성한다.
- 기존 사용자 변경을 되돌리지 않는다.

## 로컬 하네스 생성 기준

- 사용자가 로컬 하네스 생성을 승인했거나, 새 프로젝트 생성처럼 로컬 하네스가 완료 기준에 포함되는 요청이면 필요한 파일을 만든다.
- 답이 없는 항목은 임의로 확정하지 않고 `미정` 또는 `결정되지 않은 질문`으로 남긴다.
- 로컬 정책이 글로벌 정책과 충돌하면 로컬 문서에 예외 이유를 기록한다.
- 비밀값은 문서에 쓰지 않고 이름, 목적, 필요 여부만 기록한다.
- 아키텍처 항목의 답이 없으면 `architecture.md`에 `미정` 또는 `해당 없음`으로 남기고, 구현 전제에 직접 영향을 주는 항목은 사용자에게 먼저 질문한다.
- 로컬 하네스 생성 후에는 `validation.md`에 실행 가능한 검증 명령과 미실행 사유 기록 기준을 둔다.
- 로컬 하네스 문서 본문은 기본적으로 한국어로 작성하되, 파일명, 코드 식별자, 명령어, 스키마 필드명, 외부 API 이름은 원문 또는 영어를 유지한다.

## 로컬 하네스 작성 품질 기준

- `goal.md`에는 프로젝트 목적, 주요 사용자, 핵심 흐름, 제외 범위, 완료 기준이 있다.
- `context-map.md`에는 README, 실행 진입점, 주요 소스, 테스트, 설정, 환경변수 위치가 있다.
- `domain-policy.md`에는 확정된 도메인 용어와 미정 용어가 분리되어 있다.
- `architecture.md`에는 프로젝트 형태, 실행 환경, 기술 스택, 애플리케이션 구조, 통신 방식, 데이터 저장소, 비동기 처리, 인증/권한, 운영 요구, 변경 가능성이 있다.
- 외부 연동이 있으면 `architecture.md` 또는 연결된 문서에 인터페이스 문서 위치와 최소 계약이 있다.
- `tools.md`에는 설치, 실행, 테스트, 빌드, 린트 명령과 승인 필요한 작업이 있다.
- `validation.md`에는 자동 검증, 수동 검증, 실패 보고 기준이 있다.
- `handoff-log.md`에는 최초 생성 기록과 남은 질문이 있다.
- `handoff-log.md`의 `현재 기록`이 5개를 넘으면 오래된 기록을 `handoff-archive.md`로 옮기고 문서 맨 위에 아카이브 안내 문구를 남긴다.
- 알 수 없는 항목은 비워두지 않고 `미정` 또는 `해당 없음`으로 표시한다.
- 본문 언어가 한국어 기준을 따르며, 예외가 있으면 이유가 기록되어 있다.

## 완료 기준

- 프로젝트 유형이 분류됐다.
- 로컬 하네스 필요 여부가 판단됐다.
- 새 프로젝트 또는 초기 세팅이라면 파일 생성 전에 청사진이 제시됐고, 사용자의 승인 뒤 구현으로 넘어갔다.
- 필요한 경우 로컬 하네스 대화가 생성됐다.
- 새 프로젝트라면 실행, 테스트, 문서, 환경변수 기준이 남았다.
- 아키텍처 청사진이 확인됐고, 미정인 기술 결정은 `architecture.md`나 질의에 남았다.
- 기존 프로젝트라면 기존 패턴과 검증 방식이 확인됐다.
- 미정인 도메인 정책은 코드나 DB 구조로 확정되지 않았다.
