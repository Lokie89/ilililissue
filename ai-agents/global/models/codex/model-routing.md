# 모델 라우팅

이 문서는 Codex에서 작업 난이도에 맞춰 실제 모델과 추론 강도를 선택하는 기준입니다. 제품과 계정에 따라 사용 가능한 모델이 달라질 수 있으므로 존재하지 않는 추상 별칭을 런타임 설정처럼 사용하지 않습니다.

## 기본 원칙

- 기능 구현은 현재 환경에서 사용할 수 있는 가장 낮은 모델과 낮은 추론 강도로 시작한다.
- 낮은 모델이 요구사항을 충족하지 못하거나, 작업 중 복잡성·위험·불확실성이 확인될 때만 한 단계씩 상위 모델 또는 높은 추론 강도로 승격한다. 승격 이유를 작업 기록이나 최종 보고에 남긴다.
- 낮은 모델로 구현한 결과는 구현에 사용한 모델보다 높은 등급의 Reviewer 관점으로 검수한다. 검수 모델의 승격은 구현 모델의 실패를 의미하지 않으며, 품질·회귀·정책 누락을 독립적으로 확인하기 위한 기본 절차다.
- 모델을 고정할 필요가 없으면 현재 세션이나 부모 에이전트의 설정을 상속한다.
- 직접 지정할 때는 현재 환경에서 지원하는 실제 모델 ID와 `model_reasoning_effort`를 사용한다.
- 모델 이름보다 작업의 모호성, 영향 범위, 검증 난이도, 비용과 속도를 함께 고려한다.
- 지원 모델과 추론 강도는 바뀔 수 있으므로 설정을 추가하거나 변경하기 전에 현재 Codex 문서와 환경의 가용성을 확인한다.
- 고위험 작업은 높은 추론 강도만으로 안전해지지 않는다. 승인, 테스트, 독립 검토를 별도로 적용한다.

## 작업 난이도 등급

아래 등급은 판단을 돕는 문서 용어이며 Codex의 모델 별칭이 아니다.

| 등급 | 대표 작업 | 권장 방향 |
| --- | --- | --- |
| 단순 | 파일 탐색, 구조 요약, 반복 정리 | 빠른 모델 또는 낮은 추론 강도 |
| 일반 | 범위가 명확한 구현, 문서 수정 | 기본 모델과 중간 추론 강도 |
| 복잡 | 설계, 도메인 정책, 복잡한 디버깅과 리뷰 | 성능이 높은 모델과 높은 추론 강도 |
| 고위험 | 보안, 권한, 개인정보, 결제, 데이터 삭제·마이그레이션 | 지원되는 높은 추론 강도, 사람 승인, 독립 검토 |

다음 조건이 늘어날수록 더 강한 모델이나 높은 추론 강도를 고려한다.

- 요구사항이나 도메인 정책이 모호하다.
- 여러 모듈과 상태 전이에 영향을 준다.
- 실패 경로, 경계 조건, 회귀 가능성 판단이 어렵다.
- 테스트 전략이나 마이그레이션 전략부터 설계해야 한다.
- 보안, 개인정보, 재무, 법무, 의료 또는 운영 장애 위험이 있다.

작업이 명확한 읽기·검색·반복 처리로 분리되면 더 빠른 모델이나 낮은 추론 강도를 사용할 수 있다. 선택이 애매하면 현재 설정을 유지하고, 모델 변경 자체보다 컨텍스트와 완료 기준을 명확히 한다.

## 역할별 기준

| 역할 | 기본 추론 방향 | 기준 |
| --- | --- | --- |
| `planner` | 높음 | 범위, 정책, 사이드이펙트, 검증 전략 분석 |
| `domain` | 높음 | 도메인 정책 질의와 모델링 판단 |
| `implementer` | 낮음부터 시작 | 범위가 확정된 변경 구현. 막히거나 위험이 확인될 때만 승격 |
| `reviewer` | 높음 | 버그, 회귀, 테스트 갭, 유지보수성 검토 |
| `security` | 지원되는 높은 수준 | 보안, 권한, 데이터 노출 위험 분석 |
| `explorer` | 낮음~중간 | 읽기 중심 탐색과 후보 위치 확인 |
| `documenter` | 중간 | 문서, 기록, 템플릿 작성 |
| `doc-lint` | 낮음~중간 | 글로벌 모델 문서와 로컬 하네스 구조·링크·모델 간 대응 점검 |
| `product-planner` | 높음 | 프로젝트 목적, 주사용자, 연령대, 범위, 사용자 흐름 판단 |
| `ux-ui-designer` | 높음 | UX/UI, 사용성, 표현 방식, 머무는 시간과 참여 유도 판단 |
| `frontend-developer` | 중간~높음 | 컴포넌트 구조, 재사용, 프론트엔드·앱 구현 전략 |
| `backend-developer` | 높음 | 도메인 우선 백엔드 설계, 아키텍처 정합성, 테스트 우선 개발 |
| `database-specialist` | 높음 | Entity와 DBMS 적합성, 스키마, 인덱스, 제약, 마이그레이션 |
| `product-tester` | 중간~높음 | 타겟 사용자 관점의 사용성, UX/UI, 개선 제안 검토 |

역할 기본값보다 실제 작업 위험이 우선한다. 예를 들어 구현 역할이라도 인증이나 데이터 마이그레이션을 다루면 추론 강도를 높이고 별도 검토를 둔다.

## 구현·승격·검수 절차

1. 구현 전에는 요구사항과 검증 기준을 확정하고, 구현은 가장 낮은 가용 모델과 낮은 추론 강도로 시작한다.
2. 구현 모델이 문제를 해결하지 못하거나 다음 단계의 판단이 필요하면 필요한 범위만 상위 모델로 승격한다. 예: 요구사항 해석 실패, 반복되는 검증 실패, 복수 모듈 설계, 보안·권한·개인정보, 데이터 손실·마이그레이션, 되돌리기 어려운 변경.
3. 구현이 끝나면 구현 모델보다 높은 등급의 `reviewer`를 사용해 diff, 테스트 갭, 회귀, 정책 위반, 사이드이펙트를 검수한다. 고위험 작업은 높은 추론 강도와 사람 승인·독립 검토를 추가한다.
4. 리뷰 결과가 요구사항·정책·설계를 바꾸면 Planner로 되돌리고, 같은 승격 기준을 다시 적용한다.

단순 탐색·반복 정리에는 구현 모델보다 낮은 모델을 사용할 수 있다. Planner, Domain, Reviewer의 높은 기본값은 구현 자체가 아니라 판단과 독립 검수에 적용한다.

## Codex 설정 방식

저장소 기본값은 신뢰된 프로젝트의 `.codex/config.toml`, 개인 기본값은 `~/.codex/config.toml`에 둔다. 일회성 선택은 현재 세션이나 실행 옵션으로 제한한다.

커스텀 에이전트는 YAML frontmatter가 아니라 `.codex/agents/<name>.toml`에 정의한다. 기본 필드는 다음과 같다.

```toml
name = "reviewer"
description = "Correctness, regression, and test-gap reviewer."
model = "<available-model-id>"
model_reasoning_effort = "high"
sandbox_mode = "read-only"
developer_instructions = """
Review the requested diff and report concrete findings first.
"""
```

- `name`, `description`, `developer_instructions`는 커스텀 에이전트의 핵심 필드다.
- `model`과 `model_reasoning_effort`를 생략하면 명시적 spawn 값, `[agents]` 기본값, 부모 설정 순으로 상속된다.
- 지원되는 추론 강도는 모델마다 다를 수 있으므로 값을 고정하기 전에 확인한다.
- 탐색과 리뷰 에이전트는 가능한 경우 `sandbox_mode = "read-only"`로 제한한다.
- 전역 서브에이전트 기본값과 동시 실행 한도는 `.codex/config.toml`의 `[agents]`에서 관리한다.

## 로컬 매핑

같은 프로젝트에서 Claude도 함께 쓰면 Codex의 단순/일반/복잡/고위험 등급과 Claude의 모델 별칭·추론 강도를 `local/<project-name>/model-routing-map.md`에 매핑해 둔다. 작성 예시는 `local/_template/model-routing-map.md`와 `local/sample-project/model-routing-map.md`를 참조한다.

## 멀티 에이전트 선택

- 사용자의 별도 요청이 없어도, 독립적인 하위 작업이 병렬 실행으로 시간 또는 품질을 실질적으로 개선하면 서브에이전트를 자동으로 사용한다. 단순 작업에 위임을 강제하지 않는다.
- 다음 중 하나에 해당하면 자동 위임을 우선 검토한다: 서로 독립적인 탐색·테스트·로그 분석, 전문 관점이 필요한 설계 또는 리뷰, 두 개 이상 모듈의 독립 변경, 보안·권한·데이터 변경처럼 독립 검토가 필요한 고위험 작업.
- 단일 파일의 명확한 수정, 순차 의존성이 강한 작업, 위임 준비·결과 통합 비용이 더 큰 작업, 동일 파일을 동시에 수정해야 하는 작업은 직접 처리한다.
- 위임 전에 작업을 읽기·검토와 쓰기 작업으로 분리한다. 탐색·검토는 읽기 전용 에이전트에 맡기고, 쓰기가 필요하면 파일 소유 범위를 겹치지 않게 명시한다.
- 각 서브에이전트는 역할에 맞는 현재 환경의 실제 모델과 지원되는 `model_reasoning_effort`를 선택한다. 단순 탐색은 낮음~중간, 범위가 확정된 구현은 중간, 설계·리뷰·보안은 높음을 우선하며, 현재 환경에서 모델을 확인할 수 없으면 부모 설정을 상속한다.
- 코드 탐색, 테스트, 로그 분석, 독립 리뷰처럼 경계가 분명한 읽기 중심 작업을 우선 위임한다.
- 코드 리뷰나 커밋 전 diff 점검에는 `.codex/agents/reviewer.toml`을 우선 고려한다.
- 인프라, 백엔드, 프론트엔드의 보안 위험을 점검하는 계획·변경·구현 검토에는 `.codex/agents/security-reviewer.toml`을 우선 고려한다. 이 에이전트는 읽기 전용으로 증거 기반의 위험을 보고하며, 보안 보증이나 자동 수정은 수행하지 않는다.
- 문서 하네스 자체 점검이나 모델 간 정책 대응 확인에는 `.codex/agents/doc-lint.toml`을 우선 고려한다.
- 하네스, 에이전트 운영 정책, 검증 기준, 실패 케이스, 산출물 스키마처럼 문서화 판단이 핵심인 토론에는 기본 커스텀 에이전트 `.codex/agents/harness-deliberator.toml`을 우선 고려한다.
- 제품·기능 토론에는 기본 커스텀 에이전트 세트인 `.codex/agents/product-planner.toml`, `.codex/agents/ux-ui-designer.toml`, `.codex/agents/frontend-developer.toml`, `.codex/agents/backend-developer.toml`, `.codex/agents/database-specialist.toml`, `.codex/agents/product-tester.toml`을 목적에 맞게 조합한다.
- 더 나은 의견 형성이 목표인 작업은 공통 하네스의 `global/harness/deliberation.md`를 따라 Orchestrator가 독립 의견, 비판, 수정, 합성, 검증 라운드를 통제한다.
- 숙의형 작업은 단순 다수결을 사용하지 않고 근거 품질, 정책 적합성, 반대 근거, 남은 리스크를 기준으로 판단한다.
- 같은 파일을 동시에 수정하는 write-heavy 병렬 작업은 충돌과 조정 비용이 크므로 피한다.
- 병렬 쓰기가 꼭 필요하면 작업 파일을 겹치지 않게 나누거나 별도 worktree를 사용한다.
- 위임 프롬프트에는 범위, 이미 확인한 사실, 기대 산출물, 쓰기 허용 여부를 포함한다.
- 최종 책임은 주 에이전트에 있다. 위임 결과를 검증 없이 채택하지 않으며, 권한 상승·파괴적 작업·외부 상태 변경에 필요한 사용자 승인을 서브에이전트 위임으로 우회하지 않는다.

## 검증

- 현재 환경에서 모델 ID와 `model_reasoning_effort`가 지원되는지 확인한다.
- 커스텀 에이전트 파일이 TOML 문법과 Codex 설정 스키마를 따르는지 확인한다.
- 모델이나 추론 강도를 고정한 이유가 비용, 속도 또는 재현성 측면에서 설명 가능한지 확인한다.
- 고위험 작업에 승인과 독립 검토가 모델 선택과 별도로 포함됐는지 확인한다.
- 자동 위임 여부와 선택하지 않은 이유가 작업 규모, 독립성, 위험도에 비추어 설명 가능한지 확인한다.
