# 작업 상태 전이

Codex 작업은 아래 상태를 기준으로 진행한다. 단순 질의처럼 실행이 필요 없는 요청은 `observe`에서 바로 `respond`로 이동할 수 있다.

## 상태

| 상태 | 의미 | 다음 상태 |
| --- | --- | --- |
| `observe` | 사용자 요청과 저장소 기준을 읽는다. | `plan`, `ask`, `respond` |
| `plan` | 목적, 범위, 정책, 검증 기준을 정리한다. | `ask`, `implement`, `respond` |
| `ask` | 임의 결정 위험이 큰 질문을 사용자에게 제시한다. | `plan`, `implement` |
| `implement` | 승인된 변경을 최소 범위로 적용한다. | `validate` |
| `validate` | 테스트, 빌드, 린트, 문서 검증을 수행한다. | `review` |
| `review` | diff, 위험, 누락 테스트, 정책 위반을 확인한다. | `plan`, `record`, `implement` |
| `record` | handoff와 결과 보고에 남길 내용을 정리한다. | `respond` |
| `respond` | 사용자에게 결과, 검증, 남은 리스크를 보고한다. | 완료 |

## 전이 조건

### `observe`에서 `plan`

- 요청이 코드, 문서, 설정 변경을 포함한다.
- 도메인 정책, 모델 선택, 검증 전략 판단이 필요하다.
- 사용자가 청사진, 계획, 리뷰, 구현을 요청했다.

### `observe`에서 `respond`

- 저장소 변경 없이 답할 수 있는 단순 질문이다.
- 명령 실행 없이도 충분한 근거가 이미 있다.

### `plan`에서 `ask`

- 새 개념, 상태, 권한, 생명주기, 불변 조건이 불명확하다.
- 사용자의 의도를 합리적으로 추정하면 데이터 손실, 보안, 범위 확대 위험이 있다.
- 로컬 정책과 글로벌 정책이 충돌하지만 예외 이유가 없다.

### `plan`에서 `implement`

- 사용자가 실행을 승인했거나 요청 자체가 명확한 구현 요청이다.
- 단, 새 프로젝트 생성이나 초기 세팅 요청은 명확한 구현 요청처럼 보이더라도 청사진 제시와 승인 이후에만 `implement`로 이동한다.
- 필요한 도메인 정책과 검증 기준이 충분히 정의됐다.
- 예상 변경 범위와 사이드이펙트가 설명 가능하다.

### `validate`에서 `review`

- 가능한 검증 명령을 실행했거나 실행하지 못한 이유를 기록했다.
- 문서 변경인 경우 링크, 필수 섹션, 예시, 로컬 충돌 여부를 확인했다.

### `review`에서 `plan`

- 요구사항 해석, 도메인 정책, 설계 범위가 바뀌어야 하는 위험을 발견했다.
- 테스트가 요구사항을 잘못 표현한다.
- 실패 케이스가 발견됐고 단순 수정으로 해결되지 않는다.

### `review`에서 `implement`

- 누락된 검증, 오탈자, 문서 링크, 좁은 범위의 보완이 필요하다.
- 요구사항 재해석 없이 바로 수정 가능하다.

### `review`에서 `record`

- 요청한 작업이 완료됐고 남은 리스크가 설명 가능하다.
- 관련 검증 결과와 실행하지 못한 검증 이유가 정리됐다.

## 금지 전이

- 관련 파일과 상태를 확인하지 않은 채 `observe`에서 곧바로 파일 변경을 시작하지 않는다.
- 청사진, 계획, 설계만 요청받은 상태에서 `implement`로 이동하지 않는다.
- 새 프로젝트 생성이나 초기 세팅 요청에서 청사진 승인 없이 `implement`로 이동하지 않는다.
- 검증을 생략한 채 `respond`에서 검증 완료처럼 말하지 않는다.
- 도메인 정책이 불명확한데 `ask` 없이 새 개념을 확정하지 않는다.
