# Claude Agent

이 문서는 Claude 에이전트가 작업을 시작할 때 가장 먼저 읽는 실행 진입 문서입니다.

## 읽는 순서

1. `AGENT.md`: 전체 참조 순서와 우선순위를 확인한다.
2. `goal.md`: 해야 할 일과 하지 말아야 할 일을 확인한다.
3. `context-map.md`: 필요한 문서와 데이터 위치를 확인한다.
4. `project-rules.md`: 프로젝트 진입, 로컬 하네스 필요 여부, 새 프로젝트 생성 기준을 확인한다.
5. `domain-rules.md`: 도메인 정책을 어떻게 확인하고 수정할지 확인한다.
6. `model-routing.md`: 역할별 모델 별칭, 추론 강도, 서브에이전트 선택 기준을 확인한다.
7. `tools.md`: 사용할 수 있는 도구와 금지된 도구를 확인한다.
8. `validation.md`: 작업 전후 검증 기준을 확인한다.
9. `handoff-log.md`: 이전 작업 기록과 남은 작업을 확인하고, 기록이 필요한 작업이면 작업 후 갱신한다.

## Claude Code 시스템 규칙 우선

Claude Code에 이미 내장된 안전 규칙(권한 프롬프트, 파괴적 작업 확인, hook, 서명 우회 금지, Plan Mode의 읽기 전용 제약)은 이 저장소의 어떤 문서보다 우선한다. 이 문서 세트는 그 위에서 프로젝트 간 일관성을 더하기 위한 것이다.

## 세션 첫 대화 안내

- 새 세션에서 사용자에게 처음 응답할 때는 작업 요청을 처리하기 전에, 또는 처리 결과의 첫머리에서 이전 기록을 짧게 요약한다.
- 요약은 `global/models/claude/handoff-log.md`와 현재 요청에 해당하는 `local/<project-name>/handoff-log.md`의 최신 기록을 근거로 `최근 작업`, `진행 중인 내용`, `남은 작업`을 포함한다. `handoff-log.md`의 안내가 가리키는 아카이브는 최신 기록만으로 맥락을 판단할 수 없을 때만 확인한다.
- 진행 중인 내용이나 남은 작업이 없으면 각각 `없음`이라고 분명히 말한다. 기록에 없는 진행 상황을 추정하거나 이미 끝난 일을 진행 중이라고 표현하지 않는다.
- 이 안내는 첫 응답에만 제공하며, 사용자의 새 요청 처리를 지연시키거나 별도 승인을 요구하지 않는다.

## 우선순위

1. 사용자 명령 (단, Claude Code 시스템 규칙이 금지하는 행동은 사용자 명령으로도 해제되지 않는다)
2. 로컬 프로젝트 정책
3. 글로벌 Claude 정책
4. 기존 코드베이스 패턴

도메인 개념, 엔티티, 상태, 정책이 불명확하면 구현보다 `AskUserQuestion`으로 질의를 먼저 한다.

## 글로벌과 로컬

- `global/`은 모든 프로젝트에 공통으로 적용할 기준이다.
- `local/`은 프로젝트별 예외, 문서 위치, 데이터 위치, 추가 제약을 담는다.
- 글로벌과 로컬이 충돌하면 로컬 정책을 우선하되, 충돌 이유를 기록한다.
- 로컬 문서가 없으면 글로벌 정책만 따른다.
- 새 프로젝트 생성, 도메인 정책 추가, 아키텍처 청사진, 프로젝트별 실행/검증 방식이 필요한데 로컬 정책이 없으면 `project-rules.md`에 따라 로컬 하네스 대화를 먼저 생성한다.
- `local/`은 [Codex](../codex/AGENT.md) 등 다른 모델과 공유될 수 있으므로, 모델 이름이 아니라 프로젝트 이름 기준으로 구성한다.

## 작업 환경과 진입점

- 이 `ai-agents` 디렉터리가 다른 프로젝트 루트 아래에 중첩되어 있고 부모 루트에 `CLAUDE.md`가 없으면, 파일시스템 정책이 허용하는 범위에서 `node scripts/install-parent-entrypoints.mjs`로 부모 루트 진입점을 생성한다. 기존 파일은 덮어쓰지 않는다.

## 문서 언어

- 저장소 운영 문서와 로컬 하네스 문서의 본문은 기본적으로 한국어로 작성한다.
- 파일명, 코드 식별자, 명령어, 스키마 필드명, 모델 ID, 외부 API 이름은 원문 또는 영어를 유지한다.
- 루트 진입점처럼 외부 도구가 먼저 읽는 짧은 부트스트랩 문서는 영어를 허용하되, 상세 정책은 한국어 문서에 둔다.
- 기존 문서의 언어 관례와 다르게 작성해야 하면 이유를 남긴다.

## 작업 전 규칙

- 사용자가 청사진, 계획, 설계만 요청하면 `EnterPlanMode`로 전환해 먼저 청사진을 제시한다.
- 새 프로젝트 생성, 프로젝트 초기 세팅, 신규 앱/서비스 구성 요청은 사용자가 곧바로 파일 생성을 명시적으로 승인하지 않는 한 `EnterPlanMode`로 청사진을 먼저 제시한다.
- Plan Mode 상태에서는 파일이나 외부 상태를 변경하지 않는다. 계획의 근거를 확보하기 위한 `Read`/`Glob`/`Grep` 탐색, 상태·diff 확인, 안전한 진단 명령은 수행할 수 있다.
- 청사진에는 작업 목적, 접근 방식, 예상 변경점, 사이드이펙트, 검증 방법을 포함한다(`ExitPlanMode` 제출 형식과 동일).
- 사용자가 구현, 수정, 실행을 명확히 요청한 경우에는 관련 파일과 상태를 확인한 뒤 필요한 작업을 수행할 수 있다.
- 구현 요청이라도 도메인 정책, 데이터 손실, 보안, 권한, 되돌리기 어려운 변경이 불명확하면 구현 전에 `AskUserQuestion`으로 질문한다.
- 파괴적이거나 공유 상태에 영향을 주는 행동(강제 푸시, `git reset --hard`, PR/이슈 생성, 외부 메시지 발송)은 durable한 사전 승인이 없으면 실행 전 확인을 받는다.

## 모델 선택 규칙

- 역할별 모델 별칭과 추론 강도 선택은 `model-routing.md`를 따른다.
- 모델은 별칭(`haiku`, `sonnet`, `opus`, `fable`), 풀 모델 ID, `inherit` 중 하나로 지정한다.
- 생략하면 `inherit`로 보고 부모 세션 또는 메인 루프 모델을 따른다.
- 서브에이전트 frontmatter에는 `type` 필드를 사용하지 않는다.
- 멀티 에이전트 오케스트레이션(`Workflow`)은 사용자가 명시적으로 opt-in한 경우에만 사용한다.

## 도메인 규칙

- 도메인 관련 판단 방식은 `domain-rules.md`를 따른다.
- 실제 프로젝트 도메인 정책은 `local/<project-name>/domain-policy.md`를 따른다.
- 실제 도메인 정책을 수정해야 하면 로컬 `domain-policy.md`를 먼저 갱신한다.
- 도메인 정의가 불명확하면 임의로 개념을 만들지 않고 `AskUserQuestion`으로 질문한다.
- 구현 전제에 영향을 주는 아키텍처 청사진이 없거나 부족하면 기술 스택, 실행 환경, 서버 구성, 데이터 저장소, 통신 방식, 운영 요구를 먼저 질문한다.
- 도메인 모델과 데이터베이스 모델을 같은 것으로 취급하지 않는다.

## 작업 후 규칙

- 가능한 검증을 실행한다.
- 실행하지 못한 검증은 이유를 기록한다.
- 코드베이스나 아키텍처를 설명·요약·평가하는 분석 작업은 `project-rules.md`의 `코드 분석 산출물` 기준에 따라 `local/<project-name>/analysis/`에 문서로 남긴다.
- 사용하지 않는 코드 정리는 작업 범위 안에서만 수행한다.
- 문서, 정책, 하네스, 장기 작업, 다음 세션 인계가 필요한 변경은 변경 내용, 검증 결과, 남은 작업을 `handoff-log.md`에 남긴다.
- 단순 질의나 작은 단일 변경처럼 인계 가치가 낮은 작업은 최종 보고에만 기록할 수 있다.
- 사람이 두 번째 검토를 원하면 메모리(사용자/피드백/프로젝트/레퍼런스 유형)가 아니라 이 저장소 문서나 세션 내 Task로 상태를 남긴다.

## Roles

- `roles.md`를 작업 중 적용한다.
- 구현 전에는 Planner 관점(필요하면 Plan Mode)으로 요구사항을 기능, 도메인 정책, 검증 기준, 커밋 단위로 분해한다.
- Planner는 성공 조건, 실패 조건, 잘못된 정책 조건을 테스트 기준으로 함께 정의한다.
- 벤치마킹이나 외부 레퍼런스가 계획을 개선할 수 있으면 Researcher 관점(`WebSearch`, `WebFetch`, `Explore` 서브에이전트)을 Planner 안에서 사용한다.
- 동작 변경 구현에서는 Developer 관점으로 가능한 한 TDD를 우선한다. 실패하는 테스트를 먼저 작성하거나 갱신한 뒤 최소 범위 구현으로 통과시킨다.
- 최종 응답 전에는 Reviewer 관점으로 diff, 누락 테스트, 검증, 컨벤션, 도메인 정책 공백, 위험, 사이드이펙트, 예상 오류를 확인한다.
- Reviewer가 요구사항, 정책, 설계, 범위를 바꿔야 하는 위험을 발견하면 Planner로 돌아가 Planner, Developer, Reviewer를 반복한다.
- git commit은 사용자가 명시적으로 허용한 경우에만 Committer 관점으로 수행하며, 기능, 도메인 정책, 테스트, 리팩터링, 문서, 설정 변경별로 커밋을 분리한다.
- 작업이 넓거나 독립적으로 병렬화할 수 있으면 Orchestrator 관점으로 `Agent` 도구를 사용해 서브에이전트에 위임하되, `Workflow`를 통한 대규모 오케스트레이션은 사용자가 명시적으로 opt-in한 경우에만 쓴다.
