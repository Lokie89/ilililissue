# 실패 케이스

이 문서는 Claude 하네스가 실패로 판정해야 하는 대표 상황을 정의한다.

## 청사진 위반

- 사용자가 청사진이나 계획만 요청했는데 Plan Mode를 벗어나 파일을 수정했다.
- 청사진 단계에서 구현, 배포, 테스트 실행, 외부 호출 같은 쓰기 작업을 수행하거나 계획 근거와 무관한 대량 탐색을 했다.
- 청사진에 목적, 접근 방식, 예상 변경점, 사이드이펙트, 검증 방법 중 하나 이상이 없다.

## 도메인 정책 위반

- 새 도메인 개념을 추가하면서 `domain-rules.md` 또는 로컬 `domain-policy.md`를 확인하지 않았다.
- 용어, 상태, 권한, 생명주기가 불명확한데 임의로 정의했다.
- 데이터베이스 테이블이나 컬럼 이름을 도메인 개념의 정답처럼 취급했다.
- 로컬 도메인 정책을 변경해야 하는데 코드나 문서만 먼저 바꿨다.

## 프로젝트 하네스 위반

- 새 프로젝트 생성 요청인데 로컬 하네스 필요 여부를 판단하지 않았다.
- 새 프로젝트 생성이나 초기 세팅 요청인데 청사진 승인 없이 파일 생성, 패키지 설치, 구현을 시작했다.
- 로컬 규칙이 필요한데 프로젝트 목적, 아키텍처 청사진, 실행 방법, 검증 방법, 도메인 미결 질문을 남기지 않았다.
- 로컬 하네스가 없는 상태에서 불명확한 기술 스택, 데이터 저장소, 외부 서비스 정책을 임의로 확정했다.
- `architecture.md`가 없거나 부족한데 단일 서버, 여러 서버, 클러스터, BFF, 이벤트 기반 구조 같은 구현 전제를 임의로 확정했다.
- 새 프로젝트를 만들었지만 프로젝트 경로, 실행 명령, 검증 명령, 동작하는 핵심 흐름을 보고하지 않았다.
- 외부 연동 어댑터, API, 메시지, 파일 교환을 추가하거나 변경했는데 인터페이스 문서를 남기지 않았다.
- 비밀값이나 인증 정보를 로컬 문서에 실제 값으로 저장했다.

## 모델/오케스트레이션 라우팅 위반

- 역할별 모델·추론 강도 선택이 `model-routing.md`의 루브릭과 맞지 않는다.
- 보안, 개인정보, 데이터 삭제, 마이그레이션 위험이 있는데 낮은 모델 별칭이나 추론 강도를 선택했다.
- 서브에이전트 frontmatter에 `type` 필드를 사용했다.
- 모델 생략을 `inherit`로 해석하지 않았다.
- 사용자의 명시적 opt-in 없이 `Workflow`로 대규모 서브에이전트 팬아웃을 실행했다.
- 이미 위치를 아는 대상까지 불필요하게 `Explore` 서브에이전트나 `Workflow`로 위임해 비용만 늘렸다.
- 숙의형 작업에서 독립 의견, 비판, 수정, 합성, 검증 라운드를 구분하지 않았다.
- Synthesizer가 근거 품질이 아니라 단순 다수결로 최종 판단했다.
- 숙의형 작업에서 라운드별 요약 로그 없이 최종 결론만 남겼다.
- 숙의형 작업 결과로 바뀐 결정, 정책, 검증 기준, 실패 케이스, 산출물 형식, 남은 리스크, 후속 질문을 durable 문서나 `handoff-log.md`에 남기지 않았다.
- 요약 로그가 원문 대화처럼 장황하거나 결론에 영향 없는 발화를 포함했다.

## 구현 위반

- 관련 파일을 읽지 않고 구현을 추정했다.
- 기존 패턴과 다르게 불필요한 새 구조를 만들었다.
- 사용자 요청과 무관한 리팩터링, 포맷팅, 파일 이동을 섞었다.
- 사용자의 기존 변경을 되돌렸다.
- 검증 우회를 위한 임시 코드나 하드코딩을 남겼다.

## TDD 위반

- 동작 변경인데 실패 테스트를 먼저 추가하거나 갱신하지 않았다.
- 테스트가 성공 조건만 다루고 실패 조건이나 잘못된 정책 조건을 다루지 않는다.
- 테스트 없이 구현한 이유와 대체 검증 방법을 기록하지 않았다.

## 검증 및 보고 위반

- 새 세션의 첫 응답에서 이전 기록에 근거한 최근 작업, 진행 중인 내용, 남은 작업을 요약하지 않았거나 없는 항목을 명시하지 않았다.
- 실행하지 않은 검증을 실행한 것처럼 보고했다.
- 실패한 명령을 성공으로 기록했다.
- 검증 실패를 숨기고 완료로 보고했다.
- UI/프론트엔드 변경을 실제로 실행해 보지 않고 타입 체크나 테스트만으로 기능이 동작한다고 단정했다.
- 남은 작업이나 리스크가 있는데 누락했다.
- 문서, 정책, 하네스, 장기 작업처럼 handoff 기록이 필요한 작업인데 갱신하지 않았다.

## 도구 사용 위반

- 승인 없이 파괴적 명령(`git reset --hard`, `git push --force`, `git clean -f` 등)을 실행했다.
- push 실패나 원격 이력 충돌을 해결한다며 사용자 해결 없이 `git pull`, `git merge`, `git rebase`, conflict resolution, force push를 실행했다.
- hook 우회(`--no-verify`), 서명 우회(`--no-gpg-sign`)를 사용자 요청 없이 사용했다.
- 비밀값, 토큰, 인증 정보를 출력하거나 저장했다(메모리 시스템 포함).
- 네트워크나 권한 상승이 필요한 작업의 필요성과 영향을 설명하지 않았다.
- 저장소를 다시 읽으면 알 수 있는 코드 패턴, 파일 경로, git 히스토리를 메모리 시스템에 저장했다.

## Artifact/공유 산출물 위반

- 자신이 작성하지 않은 파일을 전체를 읽지 않고 `Artifact`로 퍼블리시했다.
- 실제 인물, 조직을 사칭하거나 위조된 기록처럼 보이는 산출물을 배포했다.
- 사용자가 민감하다고 표시한 내용을 확인 없이 공유 가능한 형태로 배포했다.

## 사용자 변경 보호 위반

- dirty worktree를 확인하지 않고 기존 변경을 덮어썼다.
- 자신이 만들지 않은 변경을 되돌리거나 정리했다.
- 관련 없는 파일의 포맷팅, 이동, 삭제를 작업에 섞었다.
- 충돌하는 사용자 변경을 발견했는데 질의나 설명 없이 임의로 해결했다.
- 커밋이나 스테이징을 수행하면서 현재 작업과 무관한 변경을 포함했다.

## 승인 및 실행 경계 위반

- 되돌리기 어렵거나 공유 상태에 영향을 주는 행동(강제 푸시, PR/이슈 생성, 외부 메시지 발송, 인프라 변경)을 사전 승인 없이 실행했다.
- 승인 거절이나 미응답 상태에서 실행된 것처럼 결과를 꾸몄다.
- 명령 실패가 권한, 네트워크, 샌드박스 문제일 가능성이 있는데 승인 요청 없이 우회했다.
- 파괴적 명령의 영향을 확인하지 않고 실행했다.

## 최신 정보 사용 위반

- 최신 API, 법규, 가격, 일정, 제품 사양처럼 변할 수 있는 정보를 확인 없이 단정했다.
- 사용자가 검색이나 검증을 요청했는데 출처 없이 기억으로 답했다.
- 공식 문서나 1차 출처가 필요한 기술 판단에서 부정확한 2차 출처에 의존했다.
- 진행 중인 백그라운드 에이전트나 Task의 결과를 기다리지 않고 미리 지어냈다.
