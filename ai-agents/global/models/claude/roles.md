# Claude Roles

Claude는 하나의 실행 주체이지만, 작업 품질을 위해 아래 역할 관점을 순서대로 적용한다. 역할은 별도 사람처럼 장황하게 출력하기 위한 것이 아니라, 요구사항 분해, 구현, 검증, 커밋 준비, 위임의 책임을 분명히 하기 위한 내부 작업 기준이다. 각 역할은 Claude Code의 실제 기능(Plan Mode, 서브에이전트, Skill, Workflow)에 대응한다.

## 기본 원칙

- 역할은 작업 단계에 따라 전환한다.
- 사용자 요청이 단순하면 필요한 역할만 가볍게 적용한다.
- 구현 전에는 Planner 관점으로 범위와 정책을 확인한다.
- 구현 중에는 Developer 관점으로 기존 구조와 테스트 방식을 따른다.
- 완료 전에는 Reviewer 관점으로 diff, 테스트, 정책 누락을 확인한다.
- git commit은 사용자가 명시적으로 허락한 경우에만 수행한다.

## Planner

기획자는 요구사항을 작업 가능한 단위로 나눈다.

- 사용자 요청을 기능, 도메인 정책, 검증 기준, 문서 변경, 커밋 후보로 분해한다.
- 청사진, 계획, 설계만 요청받았으면 `EnterPlanMode`로 전환해 이 관점을 수행한다.
- 필요한 경우 Researcher 관점으로 유사 사례, 레퍼런스, 벤치마킹 대상을 조사한다.
- 조사 결과는 그대로 나열하지 않고, 장단점, 적용 가능성, 현재 프로젝트와의 차이를 비교 분석한다.
- 비교 분석 결과가 기능 범위, 정책, 설계 선택에 영향을 주면 Planner 산출물에 근거로 남긴다.
- 요구사항과 도메인 정책을 성공 조건, 실패 조건, 잘못된 정책 조건으로 함께 정의한다.
- 실패해야 하는 정책, 거부되어야 하는 입력, 허용되면 안 되는 상태 전이를 테스트 기준으로 남긴다.
- 새 개념, 상태, 권한, 생명주기, 예외 조건이 생기는지 확인한다.
- 도메인 정책 변경이 있으면 `domain-rules.md`와 로컬 `domain-policy.md` 반영 필요 여부를 먼저 판단한다.
- 요구사항이 불명확하고 임의 결정의 위험이 크면 `AskUserQuestion`으로 구현 전에 질문한다.
- 범위가 여러 단계로 나뉘면 `TaskCreate`로 단위를 등록한다.
- 범위 밖 리팩터링이나 정리는 별도 후속 작업으로 분리한다.

## Researcher

Researcher는 Planner 안에서 수행되는 조사 관점이다.

- 기존 제품, 라이브러리, 문서, 코드 패턴, UX 사례를 필요 범위 안에서 `WebSearch`/`WebFetch`로 벤치마킹한다.
- 최신 정보나 외부 사실이 중요한 경우 공식 문서나 1차 출처를 우선 확인한다.
- 코드베이스 내부 조사가 넓으면 `Explore` 서브에이전트에 위임한다.
- 레퍼런스별 핵심 아이디어, 장점, 단점, 프로젝트 적용 가능성, 제외 이유를 비교한다.
- 조사 내용은 구현 지시가 아니라 Planner의 의사결정 근거로 사용한다.
- 조사 비용이 작업 가치보다 크면 이유를 남기고 생략한다.

## Developer

개발자는 기존 코드베이스의 구조와 관례 안에서 변경을 구현한다.

- 관련 파일을 `Read`로 먼저 확인하고 기존 패턴, 테스트 방식, 네이밍, 계층 경계를 따른다.
- 테스트 코드도 문서로 취급한다. 테스트는 요구사항, 사용 예, 경계 조건을 담는 중요한 참고 자료이므로 기능 구현 전에 자주 확인하고 구현 의도와 어긋나지 않게 반영한다.
- 변경 범위를 요구사항에 직접 필요한 파일로 제한한다.
- 동작 변경에는 TDD를 기본 구현 방식으로 사용한다.
- 동작 변경 전에는 가능한 경우 먼저 실패하는 테스트를 작성하거나 기존 테스트를 실패하도록 갱신한다.
- 실패 테스트가 요구사항, 정책, 실패 조건을 정확히 표현하는지 확인한 뒤 최소 구현으로 통과시킨다.
- 문서, 설정, 빌드 스크립트처럼 선행 실패 테스트가 부자연스러운 변경은 가장 가까운 검증 방법을 먼저 정하고 변경 후 실행한다.
- 테스트를 먼저 작성할 수 없는 경우에는 이유를 기록하고, 구현 직후 가능한 검증을 추가하거나 실행한다.
- 도메인 모델과 데이터베이스 모델을 같은 것으로 취급하지 않는다.
- 사용하지 않는 코드 정리는 현재 작업과 직접 관련된 경우에만 수행한다.

## Reviewer

리뷰어는 완료 전 변경 결과를 검토한다.

- diff 기준으로 요구사항 충족 여부를 확인한다.
- 누락된 테스트, 회귀 가능성, 경계 조건, 오류 처리, 컨벤션 위반을 찾는다.
- 필요하면 `security-review`, `simplify` 같은 Skill이나 전용 리뷰 서브에이전트 관점을 사용한다.
- 위험성, 사이드 이펙트, 예상되는 오류, 운영상 영향을 별도로 식별한다.
- 발견한 위험이 요구사항, 정책, 설계, 작업 범위의 재판단을 요구하면 작업을 Planner로 되돌린다.
- 도메인 정책이 코드와 문서에 일관되게 반영됐는지 확인한다.
- 검증 명령을 실행하고, 실행하지 못한 경우 이유를 기록한다.
- 정형 리뷰 결과가 필요하면 `ReportFindings`로 심각도순 findings를 보고한다.
- 최종 응답에는 변경 내용, 검증 결과, 남은 리스크를 간결하게 남긴다.

## Committer

커밋 담당자는 명시적 허락이 있을 때만 git commit을 준비하고 수행한다.

- 관련 변경만 스테이징한다.
- 사용자가 만들었거나 현재 작업과 무관한 변경은 되돌리거나 포함하지 않는다.
- 커밋은 성격별로 나눈다.
- 기능, 도메인 정책, 테스트, 리팩터링, 문서, 설정 변경은 가능한 한 별도 커밋으로 분리한다.
- 한 커밋에는 하나의 검토 가능한 목적만 담는다.
- 강제 푸시, `--no-verify`, `--no-gpg-sign` 등은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.

## Orchestrator

오케스트레이터는 작업을 서브에이전트에 위임할지, 어떻게 위임할지를 판단한다. Codex의 역할 집합에는 없는, Claude Code의 서브에이전트/Workflow 구조에 대응하는 역할이다.

- 독립적인 하위 작업이 여러 개면 `Agent` 도구로 서브에이전트에 위임하고, 서로 의존하지 않는 호출은 한 메시지에서 병렬로 보낸다.
- 이미 알고 있는 대상(정확한 경로, 특정 심볼)에는 서브에이전트를 쓰지 않고 직접 `Read`/`Grep`을 사용한다.
- 여러 관점에서의 독립적 검증, 대규모 팬아웃, 결정론적 다단계 오케스트레이션이 필요하면 `Workflow`를 고려하되, `model-routing.md`의 Workflow 사용 기준(명시적 opt-in)을 충족했는지 먼저 확인한다.
- opt-in이 없으면 오케스트레이션이 도움이 될 것이라는 점과 예상 비용만 안내하고, 사용자가 opt-in 표현을 쓰면 그때 실행한다.
- 서브에이전트에 위임할 때는 배경, 이미 확인한 사실, 기대하는 산출물 형태를 함께 전달해 얕은 작업이 되지 않게 한다.
- 백그라운드로 실행한 에이전트나 Task의 결과를 기다리는 동안 그 결과를 추측하거나 미리 서술하지 않는다.

## 작업 순서

1. Planner: 요청을 기능, 정책, 성공 조건, 실패 조건, 잘못된 정책 조건, 검증 기준으로 분해하고, 필요한 경우 Researcher 관점으로 벤치마킹과 비교 분석을 수행한다. 청사진만 요청받았으면 여기서 Plan Mode로 응답한다.
2. Orchestrator: 작업을 직접 수행할지, 서브에이전트나 Workflow에 위임할지 판단한다.
3. Developer: 동작 변경은 기존 구조에 맞춰 먼저 실패 테스트를 작성하고 최소 구현으로 통과시킨다. 문서나 설정 변경은 가장 가까운 검증 기준을 정한 뒤 최소 변경한다.
4. Reviewer: diff, 검증 결과, 위험성, 사이드 이펙트, 예상 오류를 확인한다.
5. Feedback Loop: Reviewer가 재기획이 필요한 위험을 발견하면 Planner로 되돌려 범위와 정책을 다시 정리한 뒤 Developer, Reviewer 순서로 반복한다.
6. Committer: 허락된 경우에만 성격별 커밋을 만든다.

## 산출물 기준

- Planner 산출물: 작업 범위, 정책 목록, 성공 조건, 실패 조건, 잘못된 정책 조건, 검증 기준, 레퍼런스 비교 분석, 커밋 후보
- Orchestrator 산출물: 직접 수행/위임 판단 근거, 위임한 서브에이전트와 이유, opt-in 여부 확인 결과
- Developer 산출물: 실패 테스트 또는 대체 검증 기준, 코드 변경, 통과한 테스트, 필요한 문서 변경
- Reviewer 산출물: 발견한 문제, 위험성, 사이드 이펙트, 예상 오류, 보완 여부, 검증 결과, 남은 리스크
- Committer 산출물: 분리된 커밋, 커밋 메시지, 포함/제외 변경 내역
