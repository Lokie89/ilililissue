# 검증 방법

## 기본 체크리스트

- [ ] 청사진만 요청받은 경우 Plan Mode를 벗어나 실제 작업을 실행하지 않았다.
- [ ] 새 프로젝트 생성이나 초기 세팅 요청은 청사진 승인 전까지 파일 생성, 패키지 설치, 구현을 시작하지 않았다.
- [ ] 청사진에 작업 목적, 접근 방식, 변경점, 사이드이펙트, 검증 방법이 포함되었다.
- [ ] 개념 추가가 포함된 경우 도메인 정책을 먼저 확인했다.
- [ ] 프로젝트별 규칙이 필요한 경우 로컬 하네스 존재 여부를 확인했다.
- [ ] 로컬 하네스가 없거나 부족한 경우 `AskUserQuestion`으로 필요한 질문이나 미정 항목을 기록했다.
- [ ] 문서나 로컬 하네스 본문은 기본적으로 한국어로 작성했고, 파일명·코드 식별자·명령어·스키마 필드명·외부 API 이름은 필요한 경우 원문을 유지했다.
- [ ] 외부 연동 어댑터, API, 메시지, 파일 교환을 추가하거나 변경했다면 인터페이스 문서를 남겼다.
- [ ] 구현 전제에 영향을 주는 아키텍처가 필요한 경우 `local/<project-name>/architecture.md`를 확인하거나 청사진 질문을 제시했다.
- [ ] 도메인 정의가 불명확한 경우 구현 전에 질의를 제시했다.
- [ ] 도메인 모델과 데이터베이스 모델을 같은 것으로 취급하지 않았다.
- [ ] 역할별 모델/추론 강도 선택이 `model-routing.md` 기준과 일치한다.
- [ ] 도메인 정책, 보안, 인증, 시크릿, migration 관련 변경이 있었다면 `REVIEW-CHECK:` 마커로 재기획 필요 여부를 명시했다(`.claude/hooks/review-replan-check.sh` Stop hook 대상, `tools.md`의 자동 강제 장치 참조).
- [ ] `Workflow`를 사용했다면 사용자의 명시적 opt-in이 확인됐다.
- [ ] 되돌리기 어렵거나 공유 상태에 영향을 주는 행동은 실행 전 사용자 확인을 받았다.
- [ ] push 실패나 원격 이력 충돌이 발생했을 때 사용자 해결 없이 `git pull`, `git merge`, `git rebase`, conflict resolution, force push를 실행하지 않았다.
- [ ] 요청한 목표가 실제 변경에 반영되었다.
- [ ] 관련 없는 파일 변경이 없다.
- [ ] 작업 범위 안의 사용하지 않는 코드, 죽은 분기, 불필요한 주석을 정리했다.
- [ ] 기존 스타일과 패턴을 따랐다.
- [ ] 오류 처리, 경계 조건, 실패 경로를 고려했다.
- [ ] 문서가 필요한 경우 함께 갱신했다.
- [ ] 테스트 또는 빌드 명령을 실행했다.
- [ ] 실행하지 못한 검증은 이유를 기록했다.

## 코드 변경 검증

프로젝트에 해당 명령이 있으면 아래 순서로 실행한다.

1. 포맷 또는 린트
2. 타입 체크
3. 단위 테스트
4. 통합 테스트
5. 빌드

플랫폼에 맞는 셸 도구(`Bash` 또는 `PowerShell`)로 실행하고, 실행한 실제 명령과 결과를 보고에 남긴다.

## UI/프론트엔드 변경 검증

- UI나 프론트엔드 변경은 가능하면 개발 서버를 실행하고 브라우저에서 실제 동작을 확인한다.
- 골든 패스와 주요 엣지 케이스를 함께 확인하고, 다른 기능의 회귀 여부도 관찰한다.
- 브라우저로 확인할 수 없는 환경이면 타입 체크와 테스트만으로는 기능 정확성을 보장하지 못한다는 점을 명시적으로 보고한다.

## 모델 라우팅 검증

- 역할별 모델/추론 강도 선택이 `global/models/claude/model-routing.md`의 루브릭과 일치하는지 확인한다.
- 모델 지정이 별칭, 풀 모델 ID, `inherit` 중 하나인지 확인한다.
- 모델을 생략한 경우 `inherit`로 해석되는지 확인한다.
- 서브에이전트 frontmatter에 `type` 필드가 없는지 확인한다.
- `Workflow`를 호출했다면 opt-in 조건(키워드, 세션 설정, 사용자 표현, 슬래시 커맨드 지시)이 실제로 충족됐는지 확인한다.

## 숙의형 멀티 에이전트 검증

- 더 나은 의견 형성이 목표라면 `global/harness/deliberation.md`를 확인했는지 검증한다.
- 첫 라운드에서 에이전트들이 서로의 의견을 보지 않고 독립 분석을 수행했는지 확인한다.
- Critic이 선호가 아니라 구체적 반례, 약한 근거, 위험한 가정을 제시했는지 확인한다.
- Synthesizer가 단순 다수결이 아니라 근거 품질, 정책 적합성, 남은 리스크를 기준으로 최종안을 만들었는지 확인한다.
- Verifier가 최종안의 누락, 약한 근거, 추가 검증 필요 항목을 기록했는지 확인한다.
- 라운드 수, 종료 조건, 예산 초과 또는 blocked 사유가 기록됐는지 확인한다.
- 라운드별 요약 로그가 원문 대화가 아니라 핵심 주장, 반박, 수정, 남은 리스크 중심으로 짧게 기록됐는지 확인한다.
- 토론으로 결정, 정책, 검증 기준, 실패 케이스, 산출물 형식, 남은 리스크, 후속 질문이 바뀌었다면 적절한 durable 문서나 `handoff-log.md`에 반영됐는지 확인한다.

## 도메인 정책 검증

- 도메인 관련 변경이 `global/models/claude/domain-rules.md`를 참조했는지 확인한다.
- 실제 도메인 정책 변경이 필요했다면 `local/<project-name>/domain-policy.md`가 함께 갱신되었는지 확인한다.
- 새로 추가한 개념의 이름과 의미가 도메인 정책과 일치하는지 확인한다.
- 엔티티, 상태, 권한, 생명주기, 불변 조건이 문서나 코드에 일관되게 반영되었는지 확인한다.
- 도메인 정책이 불명확했던 부분은 사용자 질의와 결정 내용을 기록한다.
- 기술적 편의 때문에 도메인 의미가 왜곡되지 않았는지 확인한다.

## 데이터베이스 모델링 검증

- 도메인 모델이 개발자가 사용하는 개념과 정책을 표현하는지 확인한다.
- 데이터베이스 모델이 DBMS의 저장, 조회, 인덱싱, 제약 관리에 적합한지 확인한다.
- 테이블 구조를 이유로 도메인 개념이 왜곡되지 않았는지 확인한다.
- 도메인 모델과 데이터베이스 모델이 다르면 매핑 이유와 트레이드오프를 기록한다.
- 마이그레이션, 인덱스, 제약 조건 변경의 사이드이펙트를 확인한다.

## 아키텍처 청사진 검증

- 프로젝트 아키텍처가 구현 전제에 영향을 주면 `local/<project-name>/architecture.md`를 확인했는지 확인한다.
- `architecture.md`가 없거나 부족하면 구현 전에 기술 스택, 실행 환경, PC/서버 스펙, 배포 단위, 단일 서버/클러스터 여부, BFF/API Gateway, 통신 방식, 데이터 저장소, 비동기 처리, 인증/권한, 운영 요구 중 필요한 질문을 제시했는지 확인한다.
- 외부 연동 어댑터, SDK 래퍼, API 클라이언트, Webhook, 메시지 큐, 이벤트 브로커, 파일 교환, 배치 연동이 있으면 인터페이스 문서 위치와 최소 계약이 기록됐는지 확인한다.
- 인터페이스 문서에 연동 대상, 책임 경계, 호출 방향, 인증 방식, 요청·응답 또는 메시지 스키마, 오류·재시도·타임아웃 기준, rate limit, 멱등성, 비밀값 이름, 검증 방법이 있는지 확인한다.
- 모든 항목을 확정하지 못한 경우 `미정` 또는 `해당 없음`으로 기록하고, 현재 구현에 직접 영향을 주는 항목은 남은 질문으로 분리했는지 확인한다.
- 단일 서버, 여러 서버, 클러스터, 서버리스, 이벤트 기반 구조 같은 선택이 도메인 의미나 DB 모델을 왜곡하지 않았는지 확인한다.
- 나중에 바꿀 수 있는 결정과 바꾸기 어려운 결정이 구분됐는지 확인한다.

## 보이스카웃 규칙 검증

- 정리한 코드가 현재 작업 범위와 직접 관련되는지 확인한다.
- 삭제한 코드가 외부 API, 설정, 런타임 참조로 사용되지 않는지 확인한다.
- 죽은 코드 제거가 동작 변경을 만들 수 있다면 테스트나 근거를 남긴다.
- 범위 밖 정리가 필요해 보이면 이번 변경에 섞지 않고 남은 작업으로 기록한다.

## 문서 변경 검증

- 링크가 올바른 상대 경로를 가리키는지 확인한다.
- 프로젝트 루트 부트스트랩 정책을 변경했다면 `node scripts/bootstrap-project-root.mjs`가 기존 `AGENTS.md`, `CLAUDE.md`, `.codex/agents/*.toml`을 덮어쓰지 않는지 확인한다.
- 루트 진입 문서 생성 정책만 변경했다면 `node scripts/ensure-entrypoints.mjs`가 기존 `AGENTS.md`와 `CLAUDE.md`를 덮어쓰지 않는지 확인한다.
- nested `ai-agents/` 부모 루트 진입점 정책을 변경했다면 `node scripts/install-parent-entrypoints.mjs`가 부모 루트의 기존 `AGENTS.md`와 `CLAUDE.md`를 덮어쓰지 않는지 확인한다.
- 문서 구조가 해당 문서의 목적에 맞는 필수 섹션을 포함하는지 확인한다.
- 저장소 운영 문서와 로컬 하네스 문서의 본문이 기본적으로 한국어로 작성되었는지 확인한다.
- 파일명, 코드 식별자, 명령어, 스키마 필드명, 모델 ID, 외부 API 이름은 원문 또는 영어를 유지해도 되는 예외로 취급한다.
- 기존 문서의 언어 관례와 다르게 작성했다면 이유가 기록되어 있는지 확인한다.
- 다음 세션이 읽어도 작업 목적과 남은 일이 명확한지 확인한다.
- 새 세션의 첫 응답이 최신 handoff 기록을 근거로 최근 작업, 진행 중인 내용, 남은 작업을 요약하며, 없는 항목은 `없음`으로 밝혔는지 확인한다.
- `handoff-log.md`의 `현재 기록`이 5개를 넘으면 오래된 기록이 `handoff-archive.md`로 옮겨졌고, 아카이브 안내 문구가 남아 있는지 확인한다.

## 프로젝트 하네스 검증

- 새 프로젝트 생성이나 프로젝트별 정책이 필요한 변경이면 `global/models/claude/project-rules.md`를 확인한다.
- 로컬 하네스 필요 여부가 명확히 판단됐는지 확인한다.
- 새 프로젝트 생성이나 초기 세팅 요청이면 파일 생성 전에 청사진을 먼저 제시했는지 확인한다.
- 로컬 하네스가 필요한데 없으면 구현 전에 로컬 하네스 대화가 생성됐는지 확인한다.
- 생성된 로컬 문서가 `goal.md`, `context-map.md`, `domain-policy.md`, `architecture.md`, `tools.md`, `validation.md`, `handoff-log.md` 역할을 충족하는지 확인한다.
- 생성된 로컬 문서가 가능한 경우 `local/_template/` 구조를 따르는지 확인한다.
- 새 프로젝트는 유형별 최소 기준과 기본 완료 체크리스트를 충족하는지 확인한다.
- 새 프로젝트 완료 보고가 프로젝트 경로, 실행 명령, 검증 명령, 동작하는 핵심 흐름, 미정 항목을 포함하는지 확인한다.
- 답이 없는 정책이 `미정` 또는 `결정되지 않은 질문`으로 남았는지 확인한다.
- 비밀값이 값 자체로 기록되지 않았는지 확인한다.

## 하네스 검증

- 문서 하네스 자체를 변경했다면 `./scripts/validate-docs.sh`를 실행한다.
- 공통 숙의 패턴을 변경했다면 `global/harness/deliberation.md`가 `global/harness/README.md`, `global/harness/architecture.md`, 모델별 라우팅 또는 검증 문서에서 참조되는지 확인한다.
- 요청 유형이 `global/models/claude/harness/fixtures.md`의 어떤 케이스와 가까운지 확인한다.
- 작업 단계가 `global/models/claude/harness/state-machine.md`의 전이 조건을 만족하는지 확인한다.
- 요청 유형과 통과 기준이 `global/models/claude/harness/evaluation-rubric.md`와 맞는지 확인한다.
- 프로젝트 진입 또는 생성 요청이면 `global/models/claude/project-rules.md` 기준과 맞는지 확인한다.
- 응답 또는 기록이 `global/models/claude/harness/output-schema.md`의 필수 항목을 포함하는지 확인한다.
- 로컬 하네스 대화가 필요한 경우 `global/models/claude/harness/output-schema.md`의 로컬 하네스 대화 산출물 기준을 포함했는지 확인한다.
- `global/models/claude/harness/failure-cases.md`에 해당하는 위반이 없는지 확인한다.
- 로컬 프로젝트 정책과 글로벌 하네스 기준이 충돌하면 로컬 정책 우선 이유를 기록한다.

## 청사진 검증

- 파일이나 외부 상태 변경이 발생하지 않았는지 확인한다(Plan Mode가 `Edit`/`Write`와 쓰기성 명령을 도구 수준에서 막는다). 계획 근거를 확보하기 위한 읽기, 검색, 상태 확인, 안전한 진단 명령은 허용된다.
- 작업 내용이 사용자의 명령과 직접 연결되는지 확인한다.
- 변경되는 파일이나 동작이 구체적으로 설명되었는지 확인한다.
- 사이드이펙트가 기능, 데이터, 성능, 보안, 운영 관점에서 검토되었는지 확인한다.
- 사용자가 실행 여부를 판단할 수 있을 만큼 검증 방법과 완료 기준이 명확한지 확인한다.

## 최종 리뷰 체크

- `git status`와 필요한 `git diff`를 확인해 의도한 파일만 변경됐는지 확인한다.
- 사용자 기존 변경이나 미추적 파일을 되돌리거나 포함하지 않았는지 확인한다.
- push를 수행했다면 실패 시 원인을 보고하고 멈췄으며, 원격 변경 충돌을 임의 merge/rebase로 해결하지 않았는지 확인한다.

## 결과 보고 형식

- 변경한 파일
- 핵심 변경 내용
- 확인한 도메인 정책 또는 남은 도메인 질문
- 수정한 로컬 도메인 정책 파일
- 확인하거나 수정한 로컬 아키텍처 청사진 파일
- 도메인 모델과 데이터베이스 모델의 분리 여부
- 적용한 모델/추론 강도 선택 기준
- 위임한 서브에이전트나 Workflow(있다면 opt-in 근거)
- 실행한 검증 명령과 결과
- 실행하지 못한 검증과 이유
- 최신 정보나 외부 사실을 확인했다면 사용한 공식 문서 또는 1차 출처
- 정리한 사용하지 않는 코드 또는 정리하지 않은 이유
- 남은 작업

## TDD Validation

- [ ] 동작 변경이라면 Planner가 성공 조건, 실패 조건, 잘못된 정책 조건을 테스트 기준으로 정의했는지 확인한다.
- [ ] 동작 변경이라면 Developer가 구현 전에 가능한 실패 테스트를 먼저 작성하거나 기존 테스트를 실패하도록 갱신했는지 확인한다.
- [ ] 실패 테스트가 요구사항, 도메인 정책, 거부되어야 하는 입력, 허용되면 안 되는 상태 전이를 표현하는지 확인한다.
- [ ] 구현은 실패 테스트나 대체 검증 기준을 통과시키는 최소 범위로 제한됐는지 확인한다.
- [ ] 테스트를 먼저 작성하지 못한 경우 이유와 대체 검증 방법이 기록됐는지 확인한다.
